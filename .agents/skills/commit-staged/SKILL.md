# Commit the staged changes

Use this skill whenever the user asks to create a commit from the changes already staged in
the Git index. The defining constraint is strict: **only the index is committed, nothing else.**
No untracked file is staged, no unstaged edit is pulled in, and no unrelated work is committed.

The skill has two jobs before the commit:

1. **Enforce the code conventions** on the staged content (see `AGENTS.md` and
   `docs/development.md`). When violations exist, fix them in the working tree, then hand the
   review and staging back to the user.
2. **Validate the commit message** against the specification in `AGENTS.md` and the shape of
   the repository's recent commit messages, so the style does not drift.

## Hard rules

- The index is the only source of the commit. Use `git commit -F <file>` with no `-a`,
  no pathspec, no `--amend`, no `--no-verify`, no `--allow-empty`, no second commit.
- **Never stage anything.** Do not run `git add`, `git reset`, `git stash`, `git restore`,
  `git checkout` or `git rm`. Staging after enforcement is the user's responsibility.
- Never push, tag, merge, rebase, cherry-pick or revert.
- If the index is empty, stop and ask the user to stage the changes first.
- The index must pass the conventions checker before the commit. If the user gives the green
  light but the fixes or newly created files are not staged, do **not** commit; report exactly
  which paths are still missing and ask them to stage and reply again.
- The commit always requires an explicit affirmative green light from the user before it is
  created, including approval of the proposed commit message. An ambiguous reply means no.
- Enforcement touches only the reported violations. No refactors, no behaviour changes, no
  opportunistic formatting of unrelated files. If a fix is ambiguous or changes a public
  contract, stop and ask instead of guessing.
- Report only commands actually run; never invent a check result.

## Preconditions

Before doing anything, verify the repository state:

```shell
git rev-parse --git-dir
git status
git status --short --branch
git diff --cached --name-status
```

Stop if any of the following is true:

- `git status` shows a merge, rebase, cherry-pick, revert or bisect in progress.
- `git ls-files -u` is non-empty (unmerged entries).
- `git diff --cached --quiet` succeeds (nothing is staged).

When nothing is staged, tell the user to stage the intended changes and re-invoke the skill.
Do not stage for them.

## Snapshot the index

Record the exact state that is about to be committed, so the final commit can be verified
against it:

```shell
git write-tree
git rev-parse HEAD
git diff --cached --stat
git status --porcelain
```

Keep the `write-tree` output as `INDEX_TREE` and `HEAD` as `BASE_COMMIT`. The unstaged and
untracked entries are left untouched and are reported at the end.

## Automated conventions check

Run the bundled checker against the staged content:

```shell
python3 .agents/skills/commit-staged/scripts/check-staged-conventions.py
```

Exit code 0 means the index complies. Otherwise, fix every `ERROR` before proceeding; review
every `WARNING`.

The checker skips generated files (see the Frontend tooling section); in particular
`endurancetrio-app/src/main/resources/webpack/src/scss/utilities/endurance-icons.scss` is
never verified, since it is produced by `npm run generate:icons`.

The checker reads the staged blobs (`git show :<path>`), so it reflects exactly what would
be committed.

## Frontend tooling

For staged files under `endurancetrio-app/src/main/resources/webpack/`, run the project's own
tools in check mode against only those files, using the repository configuration:

```shell
# from endurancetrio-app/src/main/resources/webpack
npx prettier --check <staged scss/css/json/md files>
npx eslint <staged js files>
```

Do not run `npm run format`, which rewrites the whole frontend tree. If a check fails, the
fix in the next step uses `prettier --write` / `eslint --fix` on those files only.

`endurancetrio-app/src/main/resources/webpack/src/scss/utilities/endurance-icons.scss` is
generated by `npm run generate:icons` and must be excluded from these checks (and from the
automated conventions check): it is regenerated by tooling and will always differ from a
hand-formatted version. Never edit it by hand; change `icons.config.json` and rerun the
generator instead.

## Manual convention review

The checker cannot judge every rule. Read each staged blob (`git show :<path>`) and verify,
by hand, against `AGENTS.md` and `docs/development.md#code--naming-conventions`:

- **Controllers, services, repositories** — interfaces vs implementations, `Main` suffix (not
  `Impl`), method ordering (CRUD then alphabetical), helper placement.
- **Entities** — base class, `@Serial serialVersionUID`, `@Column`/converter conventions,
  associations, `equals`/`hashCode`/`toString`.
- **Tests** — class naming, package-private, fixture conventions, `underTest` naming,
  `@MockBean` avoidance in slice tests, ordering rules.
- **Flyway** — migration twins (H2/PostgreSQL), `DATABASE.md` registration, version
  uniqueness. When a new PostgreSQL DML migration is staged, also run
  `.agents/skills/port-postgres-dml-to-h2/scripts/check-h2-parity.py`.
- **Configuration** — key ordering (root and nested, `username` before `password`).
- **Frontend** — naming rules, `@forward` in `style.scss`, style-guide page update for
  new components/behaviours/icons.
- **Documentation** — `AGENTS.md`, `README.md`, `docs/` and `DATABASE.md` updated when the
  change requires it.

## Enforcement

When violations exist (automated or manual):

1. Fix them in the working tree, using the smallest possible diff.
2. Record every touched file and what was corrected.
3. Re-run the checker in worktree mode on the same file set to confirm the violations are gone:

   ```shell
   python3 .agents/skills/commit-staged/scripts/check-staged-conventions.py --source worktree
   ```

4. Then tell the user clearly:

   > The convention fixes are in the working tree, unstaged. Review them, make any
   > adjustments (for example run the linter), and stage them with `git add <paths>`.
   > Any file created by the fixes must be staged too. Only what is staged gets committed,
   > and staging a file that also has other unstaged edits pulls those edits in.

   If a touched file still has unrelated unstaged edits, warn about them by name.

If a required fix is ambiguous or would change a public contract, stop and ask instead of
guessing.

## Commit message

Before drafting, read the recent history so the message matches the house style:

```shell
git log -n 20 --format='%s'
git log -n 10 --format='%B' --no-merges
```

The house rules (from `AGENTS.md` and the recent commits) are:

- **Subject**: 50 characters or fewer, capitalized, imperative mood, no Conventional Commits
  prefix, no trailing period, no surrounding whitespace.
- **Body** (optional): a blank line after the subject, then prose paragraphs wrapped at
  72 characters, explaining what changed and why. No bullets, headings or trailers. A final
  short paragraph on tests or documentation is welcome when relevant.
- **English**, describing shipped changes; no agent/tooling chatter.
- A few older subjects exceed 50 characters — do not imitate them.

Draft the message to a temporary file outside the repository:

```shell
cat > /tmp/opencode/commit-staged-<branch>.txt <<'EOF'
Subject line

First paragraph explaining what changed and why.

Second paragraph on verification or documentation, if relevant.
EOF
```

Validate it:

```shell
python3 .agents/skills/commit-staged/scripts/check-commit-message.py \
  --file /tmp/opencode/commit-staged-<branch>.txt
```

Fix every `ERROR`; review every `WARNING`. Do not commit while the checker reports an error.

## Authorization

Before committing, always present an authorization request and wait for an explicit green
light ("approved", "proceed" or "yes"). Any other reply means no: leave the working tree as
is, report the state, and stop. The request contains:

- the proposed commit message (for approval);
- the staged file list and any paths still unstaged;
- the checks that ran and their results.

When conventions had to be enforced, also include, as a bullet list, every fixed file with a
short description of the fix applied, for example:

- `endurancetrio-app/.../endurance-expand.js` — reformatted with Prettier; replaced the
  undeclared `HTMLTableRowElement` global with `window.HTMLTableRowElement` for ESLint.
- `endurancetrio-app/.../endurance-icons.scss` — reformatted with Prettier.

Plus the diff of the fixes and the violations that triggered them.

## Green light

When the user gives the green light:

1. Re-run the index checker:

   ```shell
   python3 .agents/skills/commit-staged/scripts/check-staged-conventions.py
   ```

   If it still reports errors, do **not** commit. List the missing paths (typically the
   fixed or created files that were not staged) and ask the user to stage them and reply
   again.

2. Re-read `git diff --cached` and compare it with the recorded snapshot. If the user's
   review changed the content, update the message file and re-validate it.

3. Confirm the index tree is unchanged:

   ```shell
   git write-tree
   ```

   It must equal `INDEX_TREE`.

## Commit

```shell
git commit -F /tmp/opencode/commit-staged-<branch>.txt
```

If the commit fails (commit-msg hook, signing, identity), report the exact error and do not
bypass it with `--no-verify` or `--no-gpg-sign`.

Then verify:

```shell
git log -1 --format='%H%n%s%n%b'
git show --stat --oneline HEAD
git diff --cached --name-status
```

The last command must be empty, `HEAD` must be `BASE_COMMIT`'s child, and the commit tree
must equal `INDEX_TREE`.

## Report

Report the commit hash, subject, full body, committed files, enforcement fixes (if any),
the checks run and their results, any leftover unstaged or untracked changes, and state
explicitly that nothing was pushed.

## Deliverables

- One commit containing exactly the previously staged changes (plus any convention fixes
  the user chose to stage).
- A validated commit message following `AGENTS.md` and the repository's recent pattern.
- A report of the hash, message, files and checks. Do not push, tag or open a pull request.
